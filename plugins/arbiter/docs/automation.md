# 让它自己盯着一个目录（E-18）

> 结论先说：**这件事不要做进应用里**。用 Claude Code 自己的调度原语，零代码。
> 这条的完整论证在仓库的 `docs/RESEARCH.md` §5 与 `docs/PLAN.md` §9.1（E-18），
> 这里只留**插件使用者需要的部分**：怎么开、代价是什么、什么时候不该开。

## 先看清楚代价（最重要的一段）

⚠️ **用户关掉 Claude Code，它就停了。** 这不是一个后台服务、不是一个托盘常驻程序，
**没有「关了窗口还在跑」这回事**。它只在会话活着的那段时间里按点醒一次，
会话一结束，目录就没人看了。

这不是缺点，是**这条设计有意换来的东西**：正因为它的寿命与会话绑定，
用户不需要为「某天装的一个工具在背后默默动我的文件」去担心；也正因为如此，
它值得信任到可以被随手打开。

另外三条同样要说在明面上：

- **它不会替你删任何东西**，也不会移动源文件。转了就是旁边多一个产物。
- **它只入队，不猜**。目标格式要你说清楚，它不会「智能判断你想要什么」——
  这个项目从头到尾拒绝做那件事（`docs/PLAN.md` §9.5）。
- **要下引擎的转换不要放进来**。LibreOffice 357 MiB / Calibre 213 MiB 的下载
  是一个需要用户点头的动作，不该由一次定时唤醒在背后发起。

## 怎么开

用斜杠命令，它会先跟你确认目录、目标格式与频率，再去挂调度：

```
/arbiter:watch
```

具体实现见 `../skills/watch/SKILL.md`（那是给模型看的规程）。
它用的是宿主的原语，不是我们自造的东西：

| 原语             | 它是什么                                   | 这里怎么用                                                                               |
| ---------------- | ------------------------------------------ | ---------------------------------------------------------------------------------------- |
| `Monitor`        | 把一条命令的 stdout **每一行**当成一个事件 | 「有新文件出现」这件事最贴的形状：一条 `ls` / `Get-ChildItem` 循环，出来一行就是一次事件 |
| `CronCreate`     | 按 cron 表达式定时唤醒                     | 「每小时扫一遍」这种粗粒度轮询                                                           |
| `ScheduleWakeup` | 一次性延后唤醒                             | 「30 分钟后再看一次」的退避重试                                                          |

三者不必都用。**能用 `Monitor` 就别用轮询**——轮询在目录大的时候纯属浪费时间，
而且它每一轮都要重新判断「哪些是新的」。

## 为什么不做进应用里

因为同行做过的每一次，失败方式都很具体（`docs/RESEARCH.md` §2 有完整出处）：

- Adobe Media Encoder 的 watch folder 会把每个源文件**搬进各自的子文件夹**，
  结构被改且**没有开关**，用户抱怨横跨多年。
- WaveLab 的用户在监视目录里**录制并编辑**，10 个里 8 个失败——文件还没写完就被抓走；
  「稳定等待窗口」2 秒太短、5 分钟太长，用户最后只能放弃。
- AutoHotkey 社区那个 `WatchFolder()` 例子：同一个文件触发两次事件，
  一个 342 字节的文件让记事本开了三次窗口。

最后一条尤其致命，因为它说明**「文件写完了没有」这件事在文件系统层面没有可靠信号**。
本项目的 `renameWatcher`（M8 的「重命名即转换」）能成立，是因为它判的是
「**体积完全相等**的同词干改名」——改名不动内容，这是个能判死的判据；
而「一个新文件写完了没有」判不死，只能靠等，而等多久都是错的。

## ⚠️ 别和 M8 的「重命名即转换」互相触发

应用里那个开关（设置 → 重命名即转换）与这里的目录监视是**两套东西**，
同时开在同一个目录上会互相看得见对方的动作：

- 监视把 `a.mkv` 转成 `a.mp4` → 目录里多出一个文件 → `fs.watch` 被唤醒一次。
  它随后会重扫并做差分，而差分的判据是「同词干两侧都只有一个候选 + 体积完全相等」
  ——`a.mkv` **还在**（我们从不删源），所以这次变化不会被认成「改名」，
  **不会**触发第二次转换。但会白白唤醒一次，日志里也会多一行。
- 真正要避开的是反过来：如果用户自己把 `a.mkv` 改名成 `a.mp4`，
  M8 那条路会**把名字改回 `a.mkv` 再转一份 `a.mp4`**——而监视那条路同时也会
  看见 `a.mp4` 出现并想去转它。两条路对同一个文件各自动一次，结果是一样的产物，
  但会撞输出名（`a (1).mp4`）。

**所以：同一个目录，两个功能只开一个。** 想省心就这么记——
**「重命名即转换」适合你手上有明确动作的时候；目录监视适合你把它当投递口的时候。**

## 什么时候不该用它

- **目录在另一台机器 / 网络盘上**：轮询还好，`Monitor` 那条路会因延迟错得离谱。
- **目录里有别的东西在写**（下载目录、录屏输出目录）：文件还没写完就会被抓走，
  这正是上面 WaveLab 那个失败。宁可让下载器写完再搬进来。
- **要 7×24 不中断**：那需要一个真正的常驻服务，本项目明确不做（`docs/PLAN.md` §9.5
  的「常驻托盘 + 全自动监视目录」）。
- **想让它自动猜格式**：不做。猜错了代价是用户磁盘上多一个他没要的文件。
